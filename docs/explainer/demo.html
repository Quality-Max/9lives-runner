Locator repair: what actually ran

The recorded 9l heal tests/stale-locator.spec.ts --provider none run reproduced one failing test. Offline Tier 1 changed only the button-name literal from “Continue now” to “Continue to review”. The isolated candidate executed one test and passed the unchanged “Ready for Ada” assertion. The candidate was saved separately; the original was not applied or edited. There were zero provider calls.

“Agent + 9l” illustrates an agent reviewing the same evidence and requesting verification. It is not a recorded model response or a live Tier 2 run. If offline healing cannot find a supported repair, it returns unverified; an explicitly configured provider can propose a bounded candidate, which must still pass verification. An ambiguous target or a broken business outcome must not be hidden by weakening the assertion.

The algorithm, one decision at a time

    
This is a simplified control flow showing tool actions and decision rules. Each step is inspectable; the agent’s private reasoning is not part of the evidence.

    
agent: keep the user’s expected outcome and original assertion
agent: optionally explore with Playwright MCP
agent → 9l: run_test(spec) to reproduce the failure
agent → 9l: heal_test(spec, apply: false)

inside 9l healing:
  run the original spec again in the project
  if already passing with tests executed → return passed
  if zero tests → return unverified
  if an assertion failed → return needs_human
  if unsupported failure → return unverified
  try one supported offline locator proposal
  if needed and available → bounded provider proposals
  for each admitted proposal:
    allow only the failed action’s supported locator literal to change
    preserve assertions, imports, other actions and control flow
    execute an isolated copy with fresh evidence
    if an assertion fails → return needs_human
    if evidence is incomplete → never accept as verified
    if passed and executed count matches original → verified
  if no verified candidate → return unverified

on verified result:
  apply: false → save a .healed file for review
  apply: true  → recheck original source hash before writing
  report savedPath / applied only if the write succeeded

    
The outer agent chooses which tools to call. The optional healing provider is a separate role: it proposes a candidate when offline healing cannot finish. 9l still checks every admitted candidate. This walkthrough’s successful repair needs no provider call.

    
A receipt records execution and completeness; it does not prove that a test covers every requirement. Assessment is advisory. SDK goal completion is unverified until explicit checks establish the expected result. Verified replay and native mobile are not demonstrated here.
